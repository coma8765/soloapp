# RFC: единый client-events для WebSocket-уведомлений

Статус: предложение. Дата: 2026-10-28.

## Цель и API

Объединить приём задач, consumer и WS gateway в `client-events`. Клиент держит соединение непосредственно с ним через общий ingress; прикладные сервисы не участвуют в доставке.

- `GET /api/v1/client-events/v1/client/ws` — WebSocket upgrade с авторизацией клиента. `user_id` берётся из проверенной сессии, а не из параметров клиента. Для браузера — защищённая cookie с проверкой Origin либо одноразовый WS-ticket; долгоживущий токен не передаётся в URL.
- `POST /api/v1/client-events/v1/internal/push` — внутренний вызов с сервисной авторизацией: `idempotency_key`, `user_ids[]`, `name`, `version?`, `payload`. Ответ `202 {event_id, version}` означает сохранение задачи, не доставку. Внешнему ingress ручка недоступна.

## Схема события

- `name` — обязательное имя события, например `chat.message.created` (вместо `type`).
- `version` — timestamp в RFC 3339, UTC, с микросекундами: `2026-10-28T19:15:30.123456Z`. Отправитель может передать его в `push`; иначе ручка назначает время PG при первом сохранении. Некорректный timestamp — `400`.
- `name` и итоговая `version` сохраняются в PG и передаются в WS вместе с `event_id`, `attempt_id`, `payload`. Ответ `202` содержит `{event_id, version}`. Retry, восстановление и повтор идемпотентного запроса не меняют версию; отсутствие `version` при повторе не приводит к генерации новой.
- Timestamp не является уникальным ID или гарантией порядка между сервисами: возможны одинаковые значения и рассинхронизация часов. Дедупликация остаётся по `event_id`.

## Поток

1. `push` одной транзакцией PG сохраняет событие, адресатов и outbox. Повтор ключа возвращает прежний `event_id`; изменение `name`, адресатов, `payload` или явно переданной версии с тем же ключом — `409`.
2. Publisher внутри `client-events` публикует `event_id` в durable RabbitMQ queue с persistent message и publisher confirm. Outbox закрывается после confirm; сбой между шагами допускает дубль.
3. Consumer получает задачу с manual ACK, захватывает lease в PG и запускает попытку. Сохраняем текущий механизм межpod-доставки: PG-координация и NOTIFY будят WS-обработчики на обоих ДЦ; каждый отправляет событие своим соединениям адресатов. NOTIFY — сигнал, состояние хранится в таблицах и перепроверяется при восстановлении связи.
4. Все подключения одного `user_id` получают событие. Клиент подтверждает `event_id + attempt_id`; сервер связывает ACK с авторизованным соединением. Запись в сокет сама по себе успехом не считается.
5. После клиентских ACK consumer фиксирует receipts и `delivered` в PG, затем делает RabbitMQ ACK. Ошибка/timeout: фиксирует попытку и явно возвращает задачу на повтор с backoff и jitter. Для отложенного повтора: подтверждённая публикация в retry-очередь, затем ACK исходной задачи. Падение consumer до ACK вызывает redelivery после обнаружения разрыва.

Доставка — **at-least-once**: клиент дедуплицирует по `event_id`, сервер — по событию/соединению. Уже подтверждённые доставки пропускаются. Lease и номер попытки запрещают старому consumer завершать новую попытку. Отмена не может отозвать уже отправленный WS-frame.

## Поиск соединений и реестр PG

Прямой поиск pod для отправки не нужен: все pod `client-events` обоих ДЦ получают сигнал, каждый доставляет только своим WS. Локальный реестр: `user_id → {connection_id → WebSocketConnection}`.

| Данные в PG | Назначение |
| --- | --- |
| `ws_connections(connection_id PK, user_id, pod_instance_id, dc, lease_until, closed_at)` | Активные подключения; индекс по `user_id, lease_until`. `pod_instance_id` уникален для запуска процесса, `connection_id` — для каждого WS. |
| `delivery_targets(event_id, attempt_id, connection_id, status)` | Зафиксированный список соединений попытки; уникальность тройки. |
| `delivery_receipts(event_id, connection_id, attempt_id, ack_at)` | Подтверждения; уникальность `(event_id, connection_id)`, запись только после проверки актуальной попытки и владельца WS. |

- После авторизации pod регистрирует WS в памяти и PG; до успешной регистрации подключение не объявляется готовым. Lease продлевается пакетно только для живых соединений, закрытие отмечается в PG. Интервал продления меньше TTL; значения конфигурируемые, сроки считаются по времени PG. Ping 1 s не означает UPDATE в PG каждую секунду.
- Consumer сохраняет снимок активных соединений адресатов и `NOTIFY(event_id, attempt_id)` в транзакции. Все pod слушают одну БД на writable primary через выделенное соединение `LISTEN`; отправляют только своим `connection_id` из снимка. ACK привязывается к пользователю и соединению на сервере.
- После подключения к PG: сначала `LISTEN` + commit, затем чтение незавершённых доставок для локальных соединений. Дополнительно выполняется периодическая сверка: потерянный NOTIFY не теряет задачу. В сигнале только идентификаторы, payload читается из таблиц.

## Восстановление: pod, ДЦ и раздельные RabbitMQ

- **Падение pod:** клиент переподключается через ingress и получает новый `connection_id`; старый lease истекает. Неподтверждённая попытка считается неуспешной, следующая строит новый снимок активных соединений. Потерянное соединение не получает фиктивный ACK; новое не наследует его receipt. При отсутствии соединений у любого адресата событие остаётся pending.
- **Падение ДЦ:** после восстановления writable primary PG recovery живой площадки выбирает все просроченные незавершённые задачи, включая уже опубликованные в недоступный RabbitMQ. Проверяет `next_retry_at` и отсутствие действующего lease, атомарно резервирует восстановление и создаёт outbox для локального RabbitMQ. Один только неопубликованный outbox не покрывает такой отказ.
- **Конкуренция и возврат ДЦ:** каждый consumer атомарно захватывает lease и увеличивает номер попытки в PG. WS-обработчик проверяет актуальность перед отправкой, завершение — условным UPDATE по владельцу/номеру попытки. Старый consumer не может завершить новую попытку; уже отправленные дубли устраняет клиент. Задачи со статусом delivered в восстановившейся очереди ACK-аются без отправки. Истечение резерва публикации позволяет recovery повториться после собственного сбоя.
- **Разделение сети:** работать с задачами может только сторона с writable primary PG; без PG новые отправки и успешное завершение приостанавливаются. Нужен fencing старого primary. RabbitMQ между ДЦ не реплицируется; перенос обеспечивают PG и recovery. RTO зависит от переключения PG, reconnect, истечения lease и периода recovery. При записи в единственную копию PG последующая потеря этой копии не покрывается гарантией доставки.

## Семантика и настройки

- WebSocket Ping — **каждую 1 s** (`ws_ping_interval`); при отсутствии Pong **30 s** (`ws_pong_timeout`) watchdog закрывает соединение. Оба значения конфигурируемые. Pong не заменяет ACK события; таймаут доставки считается отдельно.
- Таймаут попытки доставки — **10 s**, application ACK watchdog — **30 s**; оба настраиваемые. Watchdog приложения не подменяется RabbitMQ consumer timeout.
- Предлагаемая граница «всем»: снимок активных соединений на начало попытки. Успех — ACK каждого соединения этого снимка для всех адресатов. Новые соединения учитываются следующей попыткой; без подключений задача остаётся pending. Разрыв соединения — не успешная доставка.
- До реализации согласовать срок хранения pending и получение истории после reconnect. Уже завершённое событие не переоткрывается для нового соединения; постоянно offline-адресат может удерживать pending бесконечно.

## Bottlenecks и отказы

| Риск | Последствие / мера |
| --- | --- |
| Много WS и медленные клиенты | RAM, файловые дескрипторы, буферы; лимиты соединений/payload, backpressure, ограниченный prefetch. Ping 1 s добавляет примерно N Ping + N Pong в секунду для N соединений. |
| Fan-out: пользователи × соединения × повторы | Все pod получают каждый сигнал; растут чтения PG, реестр, receipts и меж-ДЦ трафик. Нужны пакетирование, индексы и очистка; при росте — адресная маршрутизация по реестру. |
| Недоступен PG или его primary | Новые задачи и подтверждения не фиксируются; ACK очереди не отправляем, ждём восстановления. |
| Недоступен RabbitMQ / потерян quorum | Outbox копится. Две ноды одного локального кластера требуют обеих для quorum queue. |
| Потеря площадки | WS переподключаются; recovery переиздаёт незавершённые PG-задачи в независимый RabbitMQ живого ДЦ после истечения lease. Автоматической межкластерной redelivery нет. |
| ACK потерян, pod упал после отправки или PG commit | Повторная доставка; нужны идемпотентность и сохранённые receipts. |
| Истекла сессия, клиент offline, некорректный payload | Задачи могут повторяться бесконечно; постоянные ошибки изолируем, алертим возраст pending и число попыток. |

## Проверка перед внедрением

Два клиента одного пользователя на разных ДЦ получают событие и подтверждают его; чужой ACK отклоняется. Проверить потерю ACK, падение pod между PG commit и RabbitMQ ACK, восстановление outbox и доставку после отказа одного ДЦ. Проверить Ping 1 s и закрытие без Pong, передачу версии отправителя, назначение версии в push и её неизменность при retry. Отдельно: потеря NOTIFY, истечение lease pod, reconnect с новым ID, отказ ДЦ после publisher confirm, одновременный recovery в двух ДЦ и возврат старого consumer; задачи не теряются, ложного delivered нет.

Основание: [PostgreSQL LISTEN и порядок восстановления подписки](https://www.postgresql.org/docs/current/sql-listen.html), [NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html); [RabbitMQ acknowledgements и confirms](https://www.rabbitmq.com/docs/confirms), [consumer lifecycle и timeout](https://www.rabbitmq.com/docs/consumers).
