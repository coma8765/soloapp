# Состояние РБМК на сервере и в PostgreSQL

Общий режим использует существующий аутентифицированный WebSocket
`/api/v1/soloapp_app/v1/signal`. Управляющие команды реактора больше не идут
между браузерами через WebRTC. Голос и позы участников используют прежние
каналы независимо от состояния реактора.

## Обработка кнопки

1. Babylon picking определяет физический орган и его команду: `set`, `toggle`
   либо `delta`. Нажатие клавиши анимируется, но общее состояние локально ещё
   не меняется. Клиент показывает ожидание подтверждения.
2. Клиент посылает `reactor_command` с уникальным `requestId`. Идентификатор
   участника и пользователя сервер получает из аутентифицированной сессии,
   а не из полей, присланных браузером.
3. Сервер проверяет присутствие в комнате, имя параметра, тип, диапазон,
   допустимое действие и необходимые блокировки. `delta` вычисляется от
   последнего сохранённого значения, поэтому два нажатия `+5` дают `+10`.
4. В транзакции PostgreSQL сервер блокирует строку `planet_world`, применяет
   команду к кандидату состояния, назначает ревизию и сохраняет результат и
   квитанцию. Ошибочная команда не изменяет состояние. После успешного
   `COMMIT` клиентам отправляются снимок и подтверждение.
5. Клиент проверяет снимок и обновляет командную индикацию. Фактические
   положение стержней, обороты насосов и другие динамические состояния
   следуют модели с их задержками; подтверждённая команда не равна
   мгновенному перемещению оборудования.

Повторная отправка того же `requestId` тем же пользователем возвращает прежнюю
квитанцию, включая переподключение с новым ID участника. В базе хранится
последние 2000 квитанций и 2000 записей протокола команд. Это ограниченное
окно идемпотентности, не бессрочный аудит всех команд.

## Что хранится

Отдельное поле `planet_world.reactor` содержит JSON: полное динамическое
состояние модели v3, команды органов, ревизии, ID и эпоху вычисляющего
участника, квитанции, протокол команд и неизменяемые человеческие записи
журнала. Поле отделено от checkpoint симуляции планеты. Запись и рассылка
используют тот же транзакционный барьер, что существующее общее состояние.
Новый процесс читает данные из PostgreSQL, а не из памяти прежнего процесса
или `sessionStorage` браузера.

Записи журнала также проходят серверное подтверждение. Автор, время внесения
по часам упражнения и календарное время сервера назначаются сервером.
Ссылки исправлений, результатов и передачи смены проверяются до записи.
Получение распоряжения не закрывает его; исправления не перезаписывают старый
текст. Лимит человеческого журнала — 2000 записей; при заполнении новая запись
отклоняется явно. JSON-выгрузка остаётся средством сохранения материалов разбора.

## Где считается физика

**Этот этап добавляет серверное хранение и упорядочивание команд, но не
переносит решатель физики в C++.** Сервер выбирает вычисляющий браузер среди
участников РБМК и принимает от него снимки примерно каждые 200 мс. Снимок
принимается только при совпадении участника, эпохи и ревизии команд и после
проверки структуры, типов, диапазонов и конечности значений. Старый участник
после смены лидера не может опубликовать снимок.

Сервер доверяет выбранному браузеру численному расчёту; проверка структуры не
доказывает правильность физических уравнений. Остальные браузеры могут считать
прогноз индикации, но не публикуют его как общее состояние. Если участников
нет, упражнение сохраняется и не рассчитывается в фоне. При потере соединения
общие команды блокируются до восстановления подтверждённого состояния.

Без авторизации доступно отдельное локальное упражнение. Оно явно подписано
как локальное и не обещает сохранения в PostgreSQL. Сервер старой версии без
`reactor_protocol: 1` не включает общий режим управления.

## Миграция и порядок выпуска

Перед запуском нового backend нужно применить аддитивную миграцию из
`deploy/schema.sql` владельцем схемы:

```sql
ALTER TABLE planet_world
  ADD COLUMN IF NOT EXISTS reactor text NOT NULL DEFAULT '{}';
```

Права существующих ролей `SELECT, UPDATE` на `planet_world` достаточны;
дополнительные учётные данные приложению не нужны. Старый backend не знает
новое поле и не изменяет его при записи checkpoint планеты. Сначала выпускается
backend, затем web с новым протоколом. Диагностическая проверка владельцем БД:

```sql
SELECT id,
       reactor::jsonb ->> 'revision' AS command_revision,
       reactor::jsonb ->> 'version' AS snapshot_version,
       reactor::jsonb #>> '{state,power}' AS neutron_power,
       jsonb_array_length(coalesce(reactor::jsonb -> 'journal', '[]'::jsonb)) AS journal_entries
FROM planet_world WHERE id = 1;
```

## Проверки

`reactor_test` проверяет порядок команд, повтор после переподключения, отказ
неверных значений, смену вычисляющего участника, старые снимки и авторство
журнала. `world_store_test` выполняет команды через две независимые связи с
настоящим PostgreSQL и проверяет восстановление состояния и записей новым
процессом. `rbmk-server.test.mjs` проверяет отсутствие преждевременного
локального изменения, ACK, повторную отправку, смену лидера и совпадение
серверного профиля с исходным состоянием браузера.
