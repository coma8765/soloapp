# Участники: почты, ping и FPS

Аккаунт `a@gmail.com` видит таблицу всех подключённых сессий: почта, ping в миллисекундах и FPS. В список входят сам администратор и участники на других картах и серверных репликах. В WebXR список выводится в существующем HUD (кнопка A показывает/скрывает его). На обычном экране таблица расположена справа, под статусом соединения.

Почты также заменяют отображаемые ID в списке игроков, над аватарами, в команде БЩУ и в новых записях журнала. Числовые ID остаются внутренними ключами протокола; существующая история журнала не переписывается. Во время смешанного rollout старые узлы могут ещё не передавать почты.

## Достоверность и доступ

- `/api/v1/auth/v1/me` возвращает `user_id` и нормализованный `username` из базы auth. В игровом клиенте username — почта аккаунта. Пароль и его хэш в профиль не входят.
- Игровой сервер определяет доступ по профилю, полученному от auth после проверки bearer-токена. Email и флаг admin, присланные клиентом, не предоставляют прав. Если старый auth ещё не возвращает username, доступ к метрикам закрыт.
- Раз в секунду сервер отправляет одноразовый случайный `telemetry_probe`. Ответ того же WebSocket даёт серверный RTT; передать произвольный ping вместо измерения нельзя. FPS — сообщённое браузером значение Babylon Engine, оно не является защищённым измерением.
- Участники передаются через существующий PostgreSQL portal JSON, поэтому администратор видит клиентов обеих площадок. Изменение схемы БД не требуется. Возраст метрики учитывает монотонное время процесса и возраст удалённого heartbeat по времени БД.
- Ответ `participants` содержит ID и почту для всех клиентов, а поля `ping`/`fps` — только для администратора. Полные внутренние записи пользователей/portal наружу не передаются.
- Значения старше пяти секунд становятся неизвестными (`—`); скрытая вкладка сообщает неизвестный FPS. Выход, разрыв соединения и смена аккаунта очищают таблицу. Вышедшие сессии удаляются; аварийно исчезнувший сервер очищается по обычному TTL portal.

Ping в таблице — RTT **участник ↔ его игровой сервер**, включая обработку на клиенте, а не задержка между участниками WebRTC.

## Развёртывание

Обновить `auth`, `app-api` (C++ soloapp_app / Deployment whoami) и `web`. Рекомендуемый порядок — auth, игровой backend, web. Повторная проверка auth обновляет серверный профиль действующих сессий; новые клиенты должны загрузить актуальный web-релиз. Пользователь и пароль не создаются и не изменяются этим патчем.

## Проверки

```sh
node --test services/soloapp_app/tests/*.test.mjs
make check-codegen test-codegen

docker build --target build -t soloapp-metrics-test -f services/soloapp_app/deploy/Dockerfile .
docker build --target tests -t soloapp-auth-metrics-test -f services/auth/deploy/Dockerfile .
docker run --rm soloapp-auth-metrics-test

# Требуется пакет ws, доступный Node; NODE_PATH может указывать на временную установку.
# Для Colima: DOCKER_CONTEXT=colima-soloapp-local
python3 services/soloapp_app/tests/participants-integration.py
```

`participants-integration.py` создаёт отдельную Docker-сеть, временную PostgreSQL, настоящий auth и два игровых сервера; проверяет права, подделку полей, RTT, устаревание, переподключение и отзыв токена, затем удаляет контейнеры и сеть. Production-аккаунты и данные не используются.

Браузерная проверка `participants-browser.cjs` требует Playwright/Chrome и локальную статику на `127.0.0.1:4199` (или `PARTICIPANTS_TEST_URL`). Она использует явную UI-фикстуру восьми участников; серверная авторизация проверяется отдельным интеграционным тестом.

## Количество учёных

Под таблицей администратора находятся компактные кнопки **1–10**. Выделена подтверждённая сервером численность линейных работников; главный инженер в неё не входит. По умолчанию их семь. При увеличении новые работники входят по одному через общую дверь, при уменьшении лишние по очереди подходят к ней и выходят. Пока проход занят человеком, работник ждёт. Повторный выбор меняет цель без дублирования работников.

`workers_set` принимает целое `count` от 1 до 10, текущую `revision` и уникальный `requestId`. Сервер проверяет почту в аутентифицированном присутствии, а не поля сообщения. Устаревшая ревизия отклоняется, повторы одного запроса не применяются заново. Подтверждение — `workers_ack`, общее состояние — `workers_state`. Настройка сохраняется в `world.reactor.workers` под общей блокировкой строки PostgreSQL, переживает перезапуск сервера и не зависит от выбранного браузера-писателя реактора. Миграция не требуется.

Общее число синхронизируется через WSS, а ходьба и обход людей визуализируются каждым клиентом, как и обычные маршруты NPC. После входа в комнату отображается актуальный состав; изменение при открытой комнате проигрывается через дверь. Дверь использует существующее серверное состояние и автоматическое закрытие. При потере соединения кнопки недоступны до получения нового серверного состояния.

Дополнительные проверки: `worker-count.test.mjs`, CTest `workers_count`, `world_store_test`, сценарий двух серверов в `participants-integration.py` и `worker-count-browser.cjs` на локальной статике `127.0.0.1:4199`.
